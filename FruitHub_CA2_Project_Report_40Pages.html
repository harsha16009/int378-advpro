1. Introduction

1.1 Background

The retail and perishable grocery sector demands extremely high responsiveness and zero tolerance for order checkout failures. E-commerce platforms dealing with fresh agricultural produce face specific technological constraints: dynamic stock availability, tight delivery time windows, localized geographic dispatch, and high customer anxiety regarding order freshness. Traditional monolithic architectures group product browsing, payment gateways, and delivery tracking into a single process. Under peak load—such as morning flash sales—traffic surges to the product browsing layer can exhaust web server threads, causing payment timeouts and checkout failures.

The FruitHub Platform was developed to solve this operational fragility. By separating concerns into isolated microservices governed by an intelligent API Gateway, each business function runs in its own memory space and scales independently. Furthermore, modern software quality is fundamentally tied to its operational deployment: containerization, continuous integration, declarative orchestration, and automated observability are mandatory requirements.

1.2 Project Objectives

  • Service Isolation: Deconstruct an online fruit ordering platform into eight distinct microservices communicating over standard REST HTTP and WebSocket protocols.
  • Container Standardization: Containerize every frontend and backend component using optimized Dockerfiles, achieving consistent builds across development, testing, and production environments.
  • Declarative Orchestration: Deploy the full microservice topology to Kubernetes (Minikube) utilizing Kustomize overlays, automated rolling updates, and health probes.
  • Automated CI/CD Delivery: Build an automated delivery pipeline using Jenkins, triggered directly on code commits via GitHub webhooks over secure ngrok tunnels.
  • Deep Observability: Establish real-time infrastructure and application observability with Prometheus time-series scraping and customized Grafana visual dashboards.
  • Infrastructure as Code: Model complete cloud hosting environments for AWS ECS, VPCs, and database tiers using reusable Terraform modules.

1.3 Scope of the Report

This report covers both the application engineering of the FruitHub platform (features, frontend components, APIs, database schemas) and its comprehensive DevOps delivery lifecycle (Git workflow, Docker packaging, Kubernetes orchestration, Jenkins pipelines, Terraform IaC, Prometheus/Grafana monitoring, and incident post-mortems).

5. Database Design & Persistence Architecture

5.1 Multi-Database Isolation Pattern

In adherence to microservices best practices, domain data is strictly segregated. While all microservices connect to a single high-performance MongoDB instance in the development environment (port 27017, published to host at 27018), each service writes to a dedicated database namespace. This guarantees loose coupling and prevents database-level dependency lock-in.

5.3 Indexing, Data Modeling & Operational Guidelines

Embedding vs. Referencing Strategy

In document databases like MongoDB, choosing between embedded subdocuments and normalized references dictates performance under load:

  • Embedded Subdocuments: Used for data that is tightly coupled and bounded in size. For instance, the items array inside each Order document contains product name, quantity, and unit price captured at the moment of checkout. This prevents historical order records from altering if product catalog prices change later.
  • Referenced Documents: Used for unbounded data relationships. Users and Orders are referenced via userId strings rather than embedding an unbounded order array inside the user document.

Database Indexing Strategy

// MongoDB Index Declarations across FruitHub Services

// auth-service: Unique user email constraint
db.users.createIndex({ "email": 1 }, { unique: true });

// product-service: High-speed text & category lookups
db.products.createIndex({ "category": 1, "price": 1 });
db.products.createIndex({ "name": "text" });

// order-service: Quick retrieval of customer order history
db.orders.createIndex({ "userId": 1, "createdAt": -1 });

// chat-service: Efficient thread message pagination
db.messages.createIndex({ "threadId": 1, "timestamp": 1 });

Operational Considerations in Docker & Kubernetes

  • Data Persistence: Running MongoDB in a container without volume mounts leads to total data destruction upon container restart. In Docker Compose, a named volume (mongo-data:/data/db) is mounted. In Kubernetes, a PersistentVolumeClaim (mongo-pvc) allocates 2Gi of durable storage.
  • Connection String Management: Database credentials and connection URIs are injected strictly via environment variables (e.g., MONGO_URI=mongodb://admin:admin123@mongo:27017/order-db?authSource=admin), eliminating hardcoded secrets in application source code.

6.2 Authentication & User Security Module

The Authentication module (backend/auth-service) handles user registration and login workflows:

  • Password Protection: Passwords are never stored in plain text. During registration, passwords are processed through bcrypt.hash(password, 10).
  • Token Issuance: Upon successful verification via bcrypt.compare(), the service signs a JSON Web Token (JWT) containing userId, email, and role with a configurable expiration window.
  • Resilient Gateway Validation: The API Gateway includes intelligent token verification middleware. To support guest browsing and demo checkout modes, null, undefined, or mock tokens are accepted gracefully without throwing hard 401 Unauthorized errors on open routes.

6.3 Checkout & Simulated Payment Processing

The checkout and payment workflow spans three microservices: api-gateway, order-service, and payment-service.

Resilient Checkout Flow

  1. Order Creation: The client sends cart items, delivery address, and total amount to POST /api/orders. The order-service persists the order with status PENDING and returns an orderId.
  2. Payment Simulation & Dynamic QR Generation: The client navigates to /payment/:orderId. The frontend interacts with payment-service (port 3004). The service initiates payment records and dynamically synthesizes a UPI payment QR code string.
  3. Fallback Mechanism: If an external payment provider (e.g., Cashfree sandbox) is unreachable, the system triggers a reliable client-side QR fallback using https://api.qrserver.com/v1/create-qr-code/. This ensures the QR code is always visible and scan-ready.
  4. Verification & Transition: Upon clicking "Confirm Payment", the payment status updates to PAID, which updates the order state in order-service and dispatches a simulated alert via notification-service.
// Dynamic QR Generation & Safe Fallback (Payment.jsx snippet)
const getQrImageUrl = (dataString, amount) => {
  if (paymentDetails?.qrCodeUrl) {
    return paymentDetails.qrCodeUrl;
  }
  // Safe high-availability UPI QR fallback
  const upiPayload = `upi://pay?pa=fruithub@upi&pn=FruitHub&am=${amount}&cu=INR`;
  return `https://api.qrserver.com/v1/create-qr-code/?size=220x220&data=${encodeURIComponent(upiPayload)}`;
};

Error Handling & Payload Stream Preservation

In earlier versions of the API Gateway, standard express.json() middleware prematurely read the incoming request body stream, causing proxy timeouts on downstream POST calls. The gateway was refactored to remove global body-parsing on proxied endpoints, allowing raw multipart and JSON data streams to flow unaltered directly to domain services.

6.4 Live Geolocation Order Tracking & Support Chat

Live Google Maps Order Tracking

The OrderTracking.jsx component communicates with tracking-service (port 3006) to deliver visual delivery progress. Previous static SVG graphics were replaced with an interactive Google Maps iframe integration:

Bi-Directional Customer Support Chat (Socket.io)

Customer support is facilitated through chat-service (port 3007), operating on bi-directional WebSocket channels:

  • Gateway WebSocket Proxying: To prevent browser cross-port blocking, all WebSocket traffic connects to port 3000 (http://localhost:3000/socket.io). The API Gateway's HTTP server intercepts the upgrade header and tunnels the TCP socket directly to container chat-service:3007.
  • Pre-Seeded Conversation Threads: To eliminate blank chat windows, the client initializes a default support thread ("FruitHub Helpdesk") with an automated welcome message.
  • Simulated Auto-Responder: When a user dispatches a message, the service acknowledges delivery and generates an intelligent auto-reply within 1.5 seconds, providing immediate feedback.

7. DevOps Fundamentals and Culture

7.1 Core Engineering Principles

DevOps is a cultural and engineering methodology combining software development (Dev) with IT operations (Ops) to shorten delivery life cycles, increase deployment frequency, and deliver dependable software releases. In FruitHub, four core DevOps pillars were adopted:

  • Continuous Integration & Continuous Delivery (CI/CD): Every code commit pushed to GitHub triggers an automated build, container creation, and deployment sequence.

  • Full-Stack Observability: Proactive health tracking using Prometheus and Grafana rather than reactive manual debugging.

8. Git & GitHub Version Control Workflow

8.1 Branching Strategy & Hygiene

The FruitHub project utilizes a trunk-based development strategy centered on the main branch. Developers test changes on feature branches and merge into main via reviewed commits. Package lockfiles (package-lock.json) are strictly versioned to guarantee identical dependency trees across Docker builds, while temporary files, build directories, and environment credentials are excluded.

8.2 Large File Handling & Git Filter-Branch Recovery

During the integration of Terraform AWS infrastructure, an incident occurred where the HashiCorp AWS provider binary (terraform-provider-aws_v5.100.0_x5.exe, 685.52 MB) was accidentally staged and committed. When pushing to GitHub, the remote rejected the push: 

remote: error: File terraform/.../terraform-provider-aws.exe is 685.52 MB;

9. Microservices Architecture & API Gateway Pattern

9.1 The API Gateway Pattern

In a microservices architecture, direct client-to-microservice communication is an anti-pattern. Exposing multiple backend ports to the public internet requires complex firewall rules, forces client applications to coordinate multiple endpoint URLs, and complicates authentication.

FruitHub solves this by implementing an API Gateway running on port 3000. It acts as the single reverse proxy for the entire platform:

  • Centralized Ingress: The React frontend communicates exclusively with port 3000. The gateway inspects the URL prefix and transparently proxies requests to the appropriate backend service.
  • Cross-Origin Resource Sharing (CORS): CORS headers are configured centrally at the gateway level, eliminating repetitive and conflicting header declarations across individual microservices.
  • WebSocket Protocol Upgrades: The gateway intercepts incoming HTTP 101 Switching Protocols upgrade headers on /socket.io and pipes the TCP socket directly to chat-service:3007.

app.post('/register', async (req, res) => {

  } catch (err) {

  }
});

  try {
    const { email, password } = req.body;

11. Docker & Containerization Best Practices

11.1 Container Concepts & Multi-Stage Builds

Containerization packages an application and all its runtime dependencies, libraries, and binaries into an immutable container image. This eliminates differences between local development laptops and production servers.

11.2 Multi-Stage Dockerfile Design Pattern

FruitHub employs multi-stage Docker builds to dramatically reduce final image sizes and eliminate unnecessary build tooling from production runtime environments:

  • Stage 1 (Builder): Uses a full node:18 image to execute npm install and npm run build, compiling frontend React source files into static assets.
  • Stage 2 (Production Runtime): Uses a lightweight node:18-alpine image, copying only the compiled artifacts and production dependencies. This reduces image size from ~1.1 GB to under 160 MB.
# Multi-Stage Dockerfile (frontend/Dockerfile)
# Stage 1: Build static assets
FROM node:18 AS builder
WORKDIR /app
COPY package.json package-lock.json* ./
RUN npm cache clean --force && npm install
COPY . .
RUN npm run build

# Stage 2: Minimal Production Serving Stage
FROM node:18-alpine
WORKDIR /app
RUN npm install -g serve
COPY --from=builder /app/dist ./dist
EXPOSE 5173
CMD ["serve", "-s", "dist", "-l", "5173"]

# Backend Service Dockerfile (backend/api-gateway/Dockerfile)
FROM node:18-alpine
WORKDIR /app
COPY package.json package-lock.json* ./
RUN npm install --production
COPY . .
EXPOSE 3000
HEALTHCHECK --interval=30s --timeout=3s --start-period=5s --retries=3 \
  CMD node -e "require('http').get('http://localhost:3000/health', (r) => {if (r.statusCode !== 200) throw new Error(r.statusCode)})"
CMD ["npm", "start"]

14.1 Automated Delivery Pipeline

The FruitHub CI/CD pipeline is orchestrated using an on-premises Jenkins container running on port 8081. Jenkins has the host's Docker socket mounted (/var/run/docker.sock:/var/run/docker.sock), allowing it to build, stop, and restart Docker containers directly on the host machine.

14.2 Five-Stage Declarative Pipeline (Jenkinsfile)

pipeline {
    agent any

    options {
        skipDefaultCheckout(true)
    }

    stages {
        stage('Clone Repository') {
            steps {
                checkout scm
            }
        }

        stage('Stop Old Containers') {
            steps {
                sh '''
                    # Stop running containers and free allocated ports
                    docker compose down || true
                    docker compose -p demo-micro down || true
                    docker ps -q --filter "publish=3000" | xargs -r docker stop || true
                    docker ps -q --filter "publish=3008" | xargs -r docker stop || true
                    docker ps -q --filter "publish=5173" | xargs -r docker stop || true
                '''
            }
        }

        stage('Build Containers') {
            steps {
                sh 'docker compose build'
            }
        }

        stage('Run Containers') {
            steps {
                sh 'docker compose up -d'
            }
        }

        stage('Check Running Containers') {
            steps {
                sh 'docker ps --format "table {{.Names}}\t{{.Status}}\t{{.Ports}}"'
            }
        }
    }

    post {
        success { echo 'FruitHub Pipeline Completed Successfully!' }
        failure { echo 'Pipeline Execution Failed.' }
    }
}

15. Monitoring with Prometheus and Grafana

15.1 Pull-Based Observability Model

Prometheus operates on a pull model: rather than requiring microservices to push metrics to a centralized server, Prometheus periodically sends HTTP GET requests to configured endpoints (every 15 seconds). This prevents application slowdowns if the monitoring server becomes overloaded.

15.2 Prometheus Scrape Configuration

The Prometheus configuration file (monitoring/prometheus/prometheus.yml) defines two distinct scraping jobs:

  • Job 1 (Self Monitoring): Scrapes Prometheus internal engine metrics on localhost:9090.
  • Job 2 (Blackbox HTTP Probing): Uses Prometheus Blackbox Exporter (port 9115) to perform synthetic HTTP probes against each microservice's /health route.
# monitoring/prometheus/prometheus.yml (Extract)
global:
  scrape_interval: 15s
  evaluation_interval: 15s

scrape_configs:
  - job_name: 'prometheus'
    static_configs:
      - targets: ['localhost:9090']

  - job_name: 'blackbox-http'
    metrics_path: /probe
    params:
      module: [http_2xx]

16. DevSecOps and Application Security

16.1 STRIDE Threat Modeling Analysis

The STRIDE model was applied during architecture design to systematically identify and mitigate security risks across every microservice boundary:

Threat (STRIDE) Vulnerability Scenario FruitHub Mitigation Control
Spoofing Adversary forges user identity to inspect another customer's order. Cryptographically signed JWT tokens carrying user IDs; secret keys kept in environment variables.
Tampering Modifying fruit prices or quantities during checkout payload transfer. Total order amount recalculated server-side in order-service against database pricing.
Repudiation Customer claims order payment was never placed. Immutable payment transaction records persisted in payment-db with timestamped transaction IDs.
Information Disclosure Leaking database passwords or third-party API keys in public repositories. .gitignore rules excluding .env and Terraform provider binaries; secret scanning.
Denial of Service Traffic floods exhausting microservice container memory. Container resource constraints (CPU limits 500m, Memory 256Mi) and isolated bridge networks.
Elevation of Privilege Standard customer invoking administrator product catalog deletion APIs. Role-based access control (RBAC) middleware inspecting the role claim in signed JWTs.

16.2 Token Security & CORS Hygiene

  • JWT Expiration: Tokens have a 7-day expiration window. In production, short-lived 15-minute access tokens paired with HttpOnly refresh cookies are recommended.
  • CORS Separation: Cross-Origin Resource Sharing is enabled strictly at the API Gateway level, permitting browser requests originating from http://localhost:5173. Direct external access to internal microservice ports is restricted.
